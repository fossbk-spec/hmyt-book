Cơ chế Backup & Đồng bộ Dữ liệu Đề tài Đồ án ​

Tài liệu thiết kế nội bộ — không xuất bản lên trang VitePress công khai (không nằm trong sidebar/nav của docs/.vitepress/config.mts). Ngày thiết kế: 13/09/2026.

1. Vấn đề cần giải quyết ​

Người phụ trách môn học liên tục cập nhật đề tài đồ án cho sinh viên (thêm đề tài mới, sửa mô tả, đổi dataset gợi ý...). Trước khi có cơ chế này, toàn bộ 14 đề tài được viết dưới dạng văn bản tĩnh trực tiếp trong 1 file Markdown duy nhất: docs/du_an_mon_hoc.md (~800+ dòng, "PHẦN VI: MA TRẬN NGÂN HÀNG ĐỀ TÀI"). Cách làm này có 2 rủi ro đã từng xảy ra trong thực tế:

  1. Va chạm ghi đè giữa các đề tài. Vì tất cả đề tài nằm trong 1 file, bất kỳ script tự động nào (đồng bộ CI/CD từ dự án dreye, hoặc script đồng bộ nội bộ như sync_project.py cũ) ghi vào file này đều có nguy cơ xóa nhầm nội dung của các đề tài khác. Sự cố đã xảy ra 2 lần với đề tài day_mat và edge_ai_da_benh_ly (xem dreye/docs/reports/PHUONG_AN_DONG_BO_SACH_HOCMAYYTE_2026-09-12.md).
  2. Không có lớp kiểm tra. Văn bản tĩnh không có schema — thiếu trường, sai định dạng, hay trùng ID đề tài đều không bị phát hiện cho tới khi có người đọc thấy trên trang web.

2. Kiến trúc mới: 1 đề tài = 1 file ​

Sach_HocMayYTe/
├── papers/<slug>/                        ← PUBLIC — repo Git, sinh viên đọc trực tiếp
│   ├── references.bib
│   └── WORKFLOW_CAP_TOC.md / HUONG_DAN_SINH_VIEN.md
│
├── _private/papers/<slug>/               ← PRIVATE — .gitignore, KHÔNG commit lên git
│   ├── evisyn/config/criteria.json
│   ├── data/literature/evidence_pool_<slug>.jsonl
│   ├── data/literature/screening_<slug>.csv
│   ├── data/evidence_matrix_<slug>.json
│   ├── data/literature/prisma_<slug>.mmd
│   └── REVIEW_Y_VAN.md
│
├── docs/data/projects/<slug>.json        ← TẦNG HIỂN THỊ (tóm tắt cho bảng ma trận)
│   (tên file TRÙNG với tên thư mục papers/<slug>/)
│
├── docs/data/projects.data.js            ← LOADER VitePress (đọc + validate + gom nhóm)
│
├── docs/du_an/<slug>.md                  ← Trang chi tiết đầy đủ (nếu có), link từ JSON
│
└── docs/du_an_mon_hoc.md                 ← Trang tổng, PHẦN VI render bằng v-for
    (KHÔNG còn chứa văn bản tĩnh của từng đề tài)

Xem Mục 6 để biết chi tiết ranh giới private/public và vì sao cần tách.

2.1. docs/data/projects/<slug>.json — tầng hiển thị ​

Mỗi đề tài là 1 file JSON độc lập. Schema tối thiểu:

json
{
  "id": "3.4",
  "group": 3,
  "title": "Dự đoán nguy cơ tái nhập viện suy tim (cấp tốc)",
  "dataset": "MIMIC-IV demo / UCI Heart Failure",
  "model": "Logistic Regression + SHAP",
  "challenge": "Mất cân bằng lớp (class imbalance)",
  "link": "/du_an/suy_tim_risk_dxai"
}

Trường bắt buộc: id, group, title. Trường link là tùy chọn — nếu có, trang ma trận sẽ hiện nút "📄 Xem y văn & workflow chi tiết →" trỏ tới docs/du_an/<slug>.md tương ứng.

Sửa/thêm 1 đề tài chỉ cần sửa đúng 1 file này. Không bao giờ sửa trực tiếp phần "PHẦN VI" trong docs/du_an_mon_hoc.md.

2.2. docs/data/projects.data.js — loader có kiểm tra (guardrail) ​

File này là VitePress data loader — tự động chạy khi build/dev, đọc toàn bộ docs/data/projects/*.json, và:

  • Chặn build nếu có lỗi cú pháp JSON ở bất kỳ file nào (báo đúng tên file lỗi).
  • Chặn build nếu thiếu trường bắt buộc (id, group, title).
  • Chặn build nếu trùng id giữa 2 file (báo rõ 2 tên file xung đột).
  • Gom nhóm theo group (1-4) và sắp xếp tự nhiên theo id (vd "3.2" < "3.10", không phải so sánh chuỗi thô).
  • Khai báo watch: [...] để dev server tự rebuild khi 1 file JSON đổi.

→ Nếu ai đó (người hoặc script tự động) ghi sai dữ liệu, build sẽ đỏ ngay lập tức thay vì âm thầm xuất bản dữ liệu hỏng lên trang web.

2.3. docs/du_an_mon_hoc.md — v-for thay văn bản tĩnh ​

Đầu file có:

vue
<script setup>
import { data as projectsData } from './data/projects.data.js'
</script>

Và "PHẦN VI" giờ là 4 khối <ul><li v-for="proj in projectsData.group_N" ...> (N = 1..4), tự động vẽ toàn bộ đề tài trong nhóm N, gồm cả nút "Xem y văn" nếu đề tài có link. Không còn văn bản tĩnh nào của từng đề tài trong file này — thêm/sửa/xóa đề tài không bao giờ cần sửa file .md này nữa.

3. Vì sao đây là cơ chế "backup & đồng bộ dễ dàng, không ảnh hưởng đề tài khác" ​

Yêu cầuCách kiến trúc mới đáp ứng
Backup theo từng đề tàiMỗi đề tài là 1 file → git log -- docs/data/projects/suy_tim.json cho lịch sử/backup tách bạch của riêng đề tài đó, không lẫn với 13 đề tài còn lại.
Đồng bộ dễ dàngCI/CD từ dự án ngoài (DrEye...) hoặc script nội bộ chỉ cần ghi đúng 1 file JSON đích — không phải parse/patch 1 file Markdown khổng lồ.
Không ảnh hưởng đề tài khácVề mặt hệ thống file, ghi vào may_day.json không thể chạm tới nội dung day_mat.json. Va chạm ghi đè chéo giữa các đề tài trở nên bất khả thi ở cấp độ file.
Phát hiện lỗi sớmprojects.data.js chặn build khi dữ liệu sai schema/trùng id. scripts/audit_projects_registry.py (chạy độc lập, không cần build) phát hiện thêm: đề tài mồ côi 2 chiều, link trỏ tới trang không tồn tại.

4. Quy trình cập nhật đề tài đúng cách ​

  1. Thêm đề tài mới:

    • Tạo papers/<slug>/ với pipeline Evisyn đầy đủ (xem cấu trúc mục 2).
    • Tạo docs/data/projects/<slug>.json (copy 1 file có sẵn làm mẫu, đổi id/group/title/... — đảm bảo id chưa tồn tại).
    • (Tùy chọn) Tạo trang chi tiết docs/du_an/<slug>.md, thêm "link" vào JSON trỏ tới trang đó.
    • (Tùy chọn) Thêm mục nav/sidebar trong docs/.vitepress/config.mts.
    • Chạy python scripts/audit_projects_registry.py — phải PASSED cả 2 mục.
    • Chạy npm run docs:build — phải build thành công.

  2. Sửa đề tài có sẵn: chỉ sửa đúng 1 file docs/data/projects/<slug>.json. Không đụng tới file khác.

  3. Xóa đề tài: xóa docs/data/projects/<slug>.json (và tùy chọn xóa docs/du_an/<slug>.md, gỡ mục nav/sidebar liên quan). Chạy lại audit script để xác nhận không còn link mồ côi trỏ tới trang đã xóa.

  4. Trước khi commit bất kỳ thay đổi nào về đề tài: luôn chạy

    python scripts/audit_projects_registry.py

    Script FAIL (exit code 1) nếu có lỗi nghiêm trọng (JSON hỏng, thiếu trường, trùng id, link 404) — phải sửa trước khi commit.

5. Kiểm tra tự động sẵn có ​

Công cụKhi nào chạyPhát hiện gì

Cả 2 đã được kiểm thử bằng cách cố tình tạo lỗi (file JSON trùng id) và xác nhận báo lỗi đúng, chính xác tên file xung đột, không làm hỏng 13 đề tài còn lại.

6. Tách dữ liệu PRIVATE khỏi dữ liệu PUBLIC cho sinh viên ​

Bổ sung 13/09/2026 (sau khi rà soát): các file phụ trợ của quy trình rà soát y văn Evisyn (REVIEW_Y_VAN*.md, evisyn/config/criteria.json, data/literature/evidence_pool_*.jsonl, data/literature/screening_*.csv, data/literature/prisma_*.mmd, data/evidence_matrix_*.json) là sản phẩm nội bộ của quá trình biên soạn, không phải tài liệu học tập. Một số file trong nhóm này còn chứa tên dự án/bệnh viện thật (vd tên 1 dự án hợp tác bệnh viện khác) và trạng thái quy trình nội bộ (Gate 1/2) — không phù hợp để nằm trong repo public phục vụ sinh viên.

6.1. Ranh giới PUBLIC / PRIVATE ​

Ai đọcSinh viên (link trực tiếp từ docs/du_an/<slug>.md)Người phụ trách môn học (làm việc cục bộ)

Tiêu chíĐược link trực tiếp từ 1 trang docs/du_an/*.md nào đóSản phẩm phụ của Evisyn, không trang nào link tới

Kiểm chứng tiêu chí "được link trực tiếp": grep -rn "REVIEW_Y_VAN\|criteria.json\|evisyn/\|evidence_matrix\|evidence_pool\|screening_\|prisma_.*\.mmd" docs/du_an/*.md — chỉ references.bib và WORKFLOW_CAP_TOC.md/HUONG_DAN_SINH_VIEN.md xuất hiện.

6.2. Công cụ ​

  • scripts/split_private_public_data.py — di chuyển toàn bộ file PRIVATE từ papers/<slug>/ sang _private/papers/<slug>/ (idempotent, chạy lại an toàn — bỏ qua file đã ở đúng chỗ). Dùng khi phát hiện dữ liệu mới bị trộn lẫn (vd sau khi merge nội dung từ nơi khác).
  • .gitignore — có dòng _private/, đảm bảo thư mục này không bao giờ vô tình bị git add.

6.3. Quy tắc khi thêm đề tài mới (bổ sung Mục 4) ​

Khi chạy pipeline Evisyn cho 1 đề tài mới, toàn bộ output đi vào _private/papers/<slug>/ theo đúng cấu trúc trên. Chỉ thủ công copy sang papers/<slug>/ (repo public) đúng 2 loại file: references.bib (sau khi rà soát bỏ mọi ghi chú nội bộ trong trường note/comment — không tên dự án khác, không "Gate 1/2", không thuật ngữ quy trình) và tài liệu hướng dẫn cho sinh viên (WORKFLOW_CAP_TOC.md/HUONG_DAN_SINH_VIEN.md). Không bao giờ copy nguyên xi cả thư mục Evisyn output sang papers/.

6.4. Về lịch sử git ​

Nội dung nhạy cảm nêu trên đã tồn tại trong các commit cũ trước 13/09/2026 (đã push công khai). Quyết định: không rewrite lịch sử git (rủi ro cao, ảnh hưởng mọi người đã clone) — chỉ đảm bảo từ nay về sau không có dữ liệu private nào được commit mới. Nếu cần dọn triệt để lịch sử cũ sau này, dùng git filter-repo trên các đường dẫn đã liệt kê ở Mục 6.1 — đây là thao tác mạnh, cần user xác nhận rõ ràng trước khi thực hiện.

7. Script đã bị vô hiệu hóa ​

scripts/sync_project.py (bản gốc) từng ghi đè toàn bộ nội dung docs/du_an_mon_hoc.md bằng nội dung đọc từ 1 file mẫu cục bộ (đường dẫn ổ D: của máy cũ). Nếu chạy lại với đường dẫn nguồn đã sửa đúng, nó sẽ xóa sạch khối <script setup> + v-for hiện tại, phá vỡ toàn bộ kiến trúc ở tài liệu này. Script đã được vô hiệu hóa chủ động (in cảnh báo + exit(1)) thay vì xóa hẳn, để giữ lại lịch sử và cảnh báo bất kỳ ai vô tình chạy lại nó.

Nếu thực sự cần đồng bộ nội dung Phần I-V (khung quản lý, rubric, chính sách — phần KHÔNG do v-for quản lý) từ 1 file mẫu ngoài, cần viết lại script để chỉ thay thế đúng đoạn Phần I-V, giữ nguyên khối <script setup> và toàn bộ "PHẦN VI" nguyên vẹn.
